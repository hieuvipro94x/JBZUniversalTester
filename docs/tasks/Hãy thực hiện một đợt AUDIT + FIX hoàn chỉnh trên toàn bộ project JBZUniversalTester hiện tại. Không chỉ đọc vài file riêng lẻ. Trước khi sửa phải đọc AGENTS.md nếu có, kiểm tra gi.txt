A. AUDIT TOÀN BỘ TEST PIPELINE
==================================================

Rà từ đầu đến cuối:

D2xxBoardTransport

PHẢI KIỂM TRA CÁC INVARIANT SAU:

1. D2XX HOT PATH

D2XX reader tuyệt đối không được chờ UI.

Không được để:

FrameReceived
 -> UI Dispatcher
 -> render
 -> return về D2XX

theo kiểu synchronous.

D2XX phải đọc/decode/publish nhanh rồi tiếp tục.

Nếu subscriber TestViewModel/TestEngine có công việc nặng:
- đưa sang worker/queue phù hợp;
- hoặc xử lý logic nhanh rồi tạo immutable snapshot;
- tuyệt đối không làm FTDI reader thread đứng hàng trăm ms.

Rà:
- FrameReceived invocation;
- subscriber timing;
- async worker;
- cancellation;
- queue ownership;
- shutdown;
- disposal.

Không được tạo Task.Run vô hạn theo mỗi frame.

2. TESTENGINE KHÔNG PHỤ THUỘC UI

PASS/FAIL phải được quyết định bởi engine/state machine.

UI chỉ trình bày kết quả.

WRONG_WIRING / SHORT_CIRCUIT khi confirmed:
- phải được chốt ngay;
- không chờ DataGrid render;
- không chờ Dispatcher;
- không chờ animation/LED.

Mỗi cycle:
- DB commit đúng 1 lần;
- counter đúng 1 lần;
- relay đúng 1 sequence;
- NG dialog đúng policy;
- LOT đúng 1 lần.

3. UI DISPATCHER / COALESCING

Kiểm tra kỹ:

_enginePresentationWorkerRunning
_latestEngineUiUpdateRequest
_engineUiUpdateRevision
_engineUiLastCompletedRevision
_productionUiCycleEpoch
_engineUiUpdatesScheduled
_engineUiUpdatesRendered
_uiRequestCount
_uiDispatcherEnqueueCount
_uiRenderedCount
_continuityPreviewUiQueued
probe presentation
IO mapping UI.

Phải bảo đảm:

- tối đa 1 presentation worker;
- tối đa 1 Dispatcher operation pending cho cùng pipeline;
- snapshot mới có thể thay snapshot cũ nếu UI chưa render;
- không enqueue hàng nghìn callback cho vài chục frame;
- stale revision không được schedule lại vô hạn;
- completed/rejected revision phải advance trạng thái đúng.

Nếu log dạng:
requests=100
dispatcher_enqueued=50000
rendered=90
thì coi là bug P0 và sửa triệt để.

4. PRODUCT STATE MACHINE

State chuẩn:

WaitingForProduct
 -> TestingRealtime
 -> PassSequence hoặc Failed
 -> WaitingForRemoval
 -> WaitingForProduct

Không được rung:

WaitingForProduct
 <-> TestingRealtime

chỉ vì một frame tạm thời mất candidate.

Realtime wrong/short detection vẫn phải hoạt động ngay khi đang lắp sản phẩm.

Tách rõ:

- electrical evidence từng frame;
- presentation/lifecycle state.

Sau khi đã có bằng chứng sản phẩm và vào TestingRealtime:
không được quay về WaitingForProduct vì một frame ngắn hạn không còn candidate.

Chỉ chuyển về WaitingForProduct sau khi:
- đang ở Removal state phù hợp;
- nhận authoritative complete Production frame;
- xác nhận sản phẩm đã tháo hoàn toàn theo policy hiện tại.

5. START GATING

Nút START/TestWindow và TestEngine phải dùng cùng một nguồn sự thật.

Không để:
UI cho bấm START
nhưng engine lại báo BLOCKED.

Rà điều kiện:

- ScanHealth == Monitoring
- board connected
- !device fault
- !hardware reconfiguration
- ProductState == WaitingForProduct
- !ProductRemoved lock
- Main IO interlock clear
- đúng scan mode Production
- fresh generation hợp lệ.

Nếu TestWindow mở khi sản phẩm cũ chưa tháo:
- không ARM sai;
- hiển thị trạng thái chờ tháo;
- START disabled;
- tiếp tục monitor IO;
- khi nhận frame sạch xác nhận removal thì tự chuyển sang trạng thái sẵn sàng;
- không bắt người dùng đóng/mở TestWindow.

--------------------------------------------------

Tạo một function trung tâm.

Ví dụ về ý tưởng:

private async Task<bool> PersistSettingsAsync(bool showSuccessMessage)
{
    CommitPendingEditorValues();

    if (!ValidateSettings(out string error))
    {
        ShowValidation(error);
        return false;
    }

    SyncCompatibilityFields();

    await SaveCoreAsync();

    SettingsSaved?.Invoke(this, EventArgs.Empty);
    return true;
}

private async void Back_Click(...)
{
    if (!await PersistSettingsAsync(false))
        return;

    await ReleaseManualOutputsAsync();
    RequestClose?.Invoke(this, EventArgs.Empty);
}

--------------------------------------------------
B5. DIRTY TRACKING
--------------------------------------------------

Nếu triển khai được sạch thì thêm dirty tracking:

Settings page load:
dirty = false

User thay đổi:
dirty = true

Save success:
dirty = false

TRỞ VỀ:
if dirty:
   validate + save
else:
   close

NHƯNG:

dirty không được bị set trong:
- InitializeComponent;
- load cfg;
- InitializeComboBoxItems;
- RefreshPortsAsync;
- programmatic SelectedValue;
- ItemsSource population;
- model/config normalization.

Cần suppression gate nếu cần.

Nếu dirty tracking làm code phức tạp/rủi ro hơn:
không bắt buộc.

Có thể validate + save một lần mỗi lần TRỞ VỀ.
Một lần ghi cfg khi rời Settings là hoàn toàn chấp nhận được.
