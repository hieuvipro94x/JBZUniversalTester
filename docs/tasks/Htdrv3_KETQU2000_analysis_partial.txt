[TRACE/TÁI DỰNG HIỆN TẠI]
Đường đổi model tối ưu đang làm:
Validate path
 -> tăng model generation
 -> parse THT ở background
 -> build logic TestEngine ở background
 -> bỏ kết quả cũ nếu người dùng đã chọn model mới hơn
 -> Commit SetModel
 -> đổi requested scan range
 -> nếu số card thực sự thay đổi mới reconcile STOP/START
 -> nếu capacity giống nhau thì reuse scan đang chạy
 -> cập nhật LastThtPath, LOT, thống kê và UI.

Mục tiêu của generation là tránh lỗi race:
model A load chậm không được hoàn tất sau rồi ghi đè model B mới chọn.

============================================================
4. GIAO TIẾP BOARD / SCAN [TRACE/TÁI DỰNG]
============================================================

Board:
- FTDI D2XX
- VID/PID ID: 0x04036001
- Description: FT245R USB FIFO
- Dùng ftd2xx.dll

Các command quan trọng:
- HANDSHAKE: 8A 01 01 01
- STOP_SCAN: 8D 00 00 00
- RESET_CLEAR: 80 00 00 00
- START_SCAN: 8C 00 xx 00
  xx = số scan unit/card active.

Với 10 card:
START_SCAN = 8C 00 0A 00

Cách start:
- Nếu board chưa prepared -> chạy PrepareScan.
- Tạo decoder mới, set capacity + mode, Reset.
- Purge RX/TX đúng trước START.
- Gửi 8C 00 xx 00.
- Tăng scan generation.
- Tạo worker đọc FTDI.

Cách stop:
- Tăng generation trước để callback cũ vô hiệu.
- Gửi STOP_SCAN trước.
- Sau đó cancel reader.
- Chờ worker chết thật.
- Không đóng FTDI.
- Giữ trạng thái prepared để START lại nhanh, không INIT lại ~700 ms.

Luồng đọc:
FT_EVENT_RXCHAR
 -> FT_GetQueueStatus
 -> FT_Read tối đa buffer 65536
 -> BoardIoDecoder.Feed(raw bytes)
 -> có thể trả 0, 1 hoặc nhiều complete ScanFrame
 -> kiểm tra generation + mode
 -> PublishFrame
 -> TestViewModel/TestEngine xử lý.

============================================================
5. LUỒNG SCAN 10 CARD [TRACE/TÁI DỰNG]
============================================================

Dung lượng:
- 10 scan card x 64 I/O = 640 I/O.
- Global I/O: 1..640.
- 641 bị loại.

Frame Production tối thiểu khi đủ 640 source, không target:
- 640 x 2 byte + terminator 2 byte
= 1,282 byte.

Terminator đã hỗ trợ:
- C0 00
- C0 01

Decoder:
- RX có thể cắt giữa frame.
- C0 và byte terminator có thể bị chia sang hai FT_Read khác nhau.
- Nhiều frame có thể cùng nằm trong một FT_Read.
- Frame thiếu source vẫn có thể được nhận dạng diagnostic nhưng không được xem là complete/ARM.

Luồng logic:
START_SCAN
 -> FT_Read
 -> decoder ghép frame
 -> xác nhận complete + expected coverage
 -> map source/target thành I/O 1..640
 -> tạo topology/connection components
 -> lọc stale frame/generation/mode
 -> Probe classifier chạy song song
 -> TestEngine.ProcessFrame
 -> chỉ khi trạng thái logic thay đổi mới đẩy cập nhật UI lớn.

============================================================
6. HIỆU NĂNG 10 CARD
============================================================

Synthetic benchmark hiện có:
- 500 frame giả lập đủ 640 I/O:
  41 ms tổng
  ~0.082 ms/frame
  ~31,782,188 byte allocated
  ~63,564 byte/frame
  UI Changed = 1
  START/STOP dư = 0

- 10,000 ProcessFrame giống nhau:
  ~5 ms
  ~3,122,040 byte allocated

Điểm nóng:
1) ToHashSet / ToDictionary / ToArray mỗi frame.
2) Copy raw frame.
3) Đồng bộ Fault UI có đường O(n^2).
4) Probe classifier trên Production frame.
5) Log queue có nguy cơ tăng khi consumer/UI chậm.
6) Watchdog 10 card dài hơn.
7) WPF DataGrid layout khi nhiều network đổi cùng lúc.

Kết luận:
CPU logic thuần không phải bottleneck lớn nhất.
Rủi ro thực tế nằm ở FTDI stream + cấp phát bộ nhớ + UI + GC + logging.
Cần benchmark 10-card hardware thật trước khi coi production-ready.

8. NHỮNG GÌ CẦN LẤY TRỰC TIẾP TỪ EXE KHI MOUNT ĐƯỢC
============================================================

Khi file Htdrv3-KETQU2000.exe có thể truy cập trực tiếp, cần trích:
1) PE/ELF header thực tế để xác nhận kiến trúc CPU và compiler.
2) Import table:
   Qt5Core/Qt5Widgets/Qt5SerialPort/Qt5Sql/VISA/FTDI hoặc thư viện khác.
3) Strings:
   đường dẫn file, SQL, serial command, timeout, config keys.
4) Resource:
   icon, WAV, qm, ui/resource bundle.
5) Symbol/mangled strings:
   class/function còn sót.
6) Section entropy:
   kiểm tra packed/UPX/strip.
7) Disassembly các entry point:
   startup/main,
   load model/setup,
   barcode model switch,
   scan read callback,
   DB write,
   PASS/FAIL finalization.
8) Call graph và offset:
   hàm nào gọi hàm nào, địa chỉ RVA/VA cụ thể.
9) Nếu là Linux ARM binary/ELF thay vì PE:
   dynsym, relocations, Qt symbols, GCC mangled names, strings và objdump/Ghidra mapping.

============================================================

- Đã có bằng chứng rất mạnh để dựng lại skeleton source gốc C++/Qt nhờ Qt TS giữ source path và tên hàm.
