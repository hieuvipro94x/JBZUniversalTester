# TASK — TÍCH HỢP IN TEM TỰ ĐỘNG TỪ FILE `.tht`

Hãy phân tích TOÀN BỘ project `JBZUniversalTester` hiện tại và hoàn thiện hệ thống in label theo nguyên tắc:

**File `.tht` của mã hàng phải là nguồn cấu hình chính của nội dung tem.**

Khi test sản phẩm PASS, chương trình phải tự động:

`THT -> ProductModel -> dữ liệu runtime -> render template -> tạo payload -> gửi máy in`

Không được hard-code dữ liệu riêng cho từng mã hàng.
ĐỒNG THỜI CHỈNH LẠI PHẦN IN TEM GỌN HƠN KHÔNG CẦN NHIỀU CÀI ĐẶT NHƯ VẬY NHƯNG VẪN IN TEM PHẢI ĐÚNG

# 8. HỖ TRỢ FORMAT CỦA `SendSerial.exe` CŨ

Tool SendSerial cũ đã sử dụng dạng:

```text
$DATA$
$LOTNO$
$MODEL$
$PRODUCT$
$INTERFACE$
```

Hãy hỗ trợ alias này để template cũ có thể tiếp tục sử dụng.

Mapping canonical phải được tập trung ở MỘT nơi.

Ví dụ:

```text
$DATA$       => PRINT_DATE
$LOTNO$      => LOT_NO
$MODEL$      => PART_NUMBER hoặc trường model thật trong THT
$PRODUCT$    => PRODUCT_NAME
$INTERFACE$  => interface thật lấy từ THT
```

NHƯNG:

Không được tự giả định `$MODEL$` hoặc `$INTERFACE$`.

Phải search file `.tht`, parser và project hiện tại để xác định mapping chính xác.

# 9. HỖ TRỢ LEGACY TOKENS HIỆN TẠI

Hiện tại code có:

```text

$PARTNAME
$DATEX
```

KHÔNG được tiếp tục chỉ phát hiện rồi throw:

Hãy phân loại từng token.

Nếu project/THT hiện có đủ dữ liệu để xác định mapping thì implement mapping.

Ví dụ chỉ khi có căn cứ:

```text

$PARTNAME

```

Những token chưa thể chứng minh mapping thì:

* giữ unresolved detection;
* log chính xác token;
* không tự tạo giá trị giả.

# 20. TUYỆT ĐỐI KHÔNG IN TRÙNG

Ví dụ:

```text

```

Không dựa riêng vào timestamp.

Phải chống:

```text

ResultChanged event
CycleCompleted event
```

cùng gọi printer.

# 31. UNIT TEST

Viết test ít nhất cho:

### Case 1 — Canonical variables

Input:

```text
{PART_NUMBER}
{PRODUCT_NAME}
{LOT_NO}
```

phải render đúng.

### Case 2 — Runtime date

`TestedAt = 2026-07-31`

phải tạo:

```text
260731
20260731
```

đúng biến tương ứng.

### Case 3 — SendSerial legacy syntax

Template có:

```text
$DATA$
$LOTNO$
```

phải replace đúng sau khi mapping được xác nhận.

### Case 4 — Unknown variable

```text
{ABC_NOT_DEFINED}
```

phải FAIL render, không print.

### Case 5 — Product A/Product B

Hai file `.tht` khác nhau phải render ra label khác nhau mà không thay code.

### Case 6 — PASS

PASS phải print đúng một lần.

### Case 7 — NG

NG không print.

### Case 8 — duplicate PASS callback

Hai callback cùng CycleId chỉ được print một tem.

# 32. ACCEPTANCE TEST THỰC TẾ

Sau khi sửa xong tôi phải có khả năng:

1. Chọn file `.tht` sản phẩm A.

5. Thay toàn bộ biến bằng dữ liệu A.

Sau đó:

1. Chọn `.tht` sản phẩm B.
2. KHÔNG build lại application.
3. Test PASS.
4. Tem phải tự đổi toàn bộ nội dung sang sản phẩm B.

# 35. KẾT QUẢ CODEX PHẢI BÁO CÁO

Sau khi implement xong hãy trả cho tôi:

1. Danh sách file đã sửa.
2. THT được parse ở class nào.
3. Những field label thực sự có trong THT.
4. Bảng mapping:

```text
THT field
→ ProductModel property
→ Label variable
→ Template token
```

5. Nơi chính xác trigger auto-print sau PASS.
6. Cơ chế chống in trùng.
7. Ví dụ payload trước render.
8. Ví dụ payload sau render.
9. Kết quả build.
10. Kết quả unit test.
11. Các legacy token nào vẫn chưa xác định được mapping.
12. Không tạo file `.bak`, `.backup`, `.old` trong source tree.

Cuối cùng chạy:

```text
dotnet clean
dotnet build
dotnet test
```

và sửa hết compile error phát sinh do thay đổi này.

Không được kết thúc task chỉ bằng phân tích. Phải implement hoàn chỉnh trong project.
