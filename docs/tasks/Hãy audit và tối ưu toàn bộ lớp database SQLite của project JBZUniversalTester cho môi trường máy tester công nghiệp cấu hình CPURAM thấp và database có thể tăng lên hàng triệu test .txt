1. AUDIT DATABASE

Đọc schema hiện tại của JBZUniversalTester.db và toàn bộ code database/repository/service.

Phân tích:
- Tests
- TestHistory
- TestFaults
- ResistanceMeasurements
- WaterProofMeasurements
- Parts
- Models
- ConfigSnapshots
- ProductionRuns
- ProbeMaintenanceEvents
- ActiveTestCycles
- migration code

Tìm:
- query chạy trên UI thread
- SELECT * không cần thiết
- query không LIMIT
- OFFSET pagination lớn
- N+1 query
- database access nằm trong loop IO/test/USB/relay
- mở/đóng connection quá thường xuyên
- transaction quá nhỏ
- commit từng measurement
- duplicate reads
- synchronous database operations có thể block WPF UI
- COUNT/GROUP BY toàn bảng lớn
- query có ORDER BY nhưng index không phù hợp
- index thừa hoặc trùng
- JSON/text lớn được load khi danh sách chỉ cần summary.

2. INDEX OPTIMIZATION

Kiểm tra bằng EXPLAIN QUERY PLAN.

Ưu tiên xem xét các index sau nhưng CHỈ tạo nếu query thực tế sử dụng:

CREATE INDEX IF NOT EXISTS IX_ResistanceMeasurements_TestId
ON ResistanceMeasurements(TestId);

CREATE INDEX IF NOT EXISTS IX_WaterProofMeasurements_TestId
ON WaterProofMeasurements(TestId);

CREATE INDEX IF NOT EXISTS IX_ProbeMaintenanceEvents_PartId_OccurredAt
ON ProbeMaintenanceEvents(PartId, OccurredAt DESC);

CREATE INDEX IF NOT EXISTS IX_Tests_ModelId_ResultAt
ON Tests(ModelId, ResultAt DESC);

Đánh giá riêng:
Tests(RunId, ResultAt DESC)
Tests(ConfigId, ResultAt DESC)

Chỉ thêm hai index trên nếu code/report thực sự query theo RunId hoặc ConfigId đủ thường xuyên để bù chi phí write/index size.

Kiểm tra các index hiện có xem có index nào redundant hoặc có thể thay bằng composite index tốt hơn.

3. MANY-TO-MANY PART <-> MODEL/HARNESS

Hiện Models có PartId nên một Model chỉ thuộc một Part.

Thiết kế SchemaVersion kế tiếp để hỗ trợ:
- một Part có nhiều Models/Harness files
- một Model/Harness có thể dùng cho nhiều Parts

Thêm bảng kiểu:

PartModels
(
    PartId INTEGER NOT NULL,
    ModelId INTEGER NOT NULL,
    IsDefault INTEGER NOT NULL DEFAULT 0,
    FirstUsedAt TEXT,
    LastUsedAt TEXT,
    PRIMARY KEY (PartId, ModelId),
    FOREIGN KEY (PartId) REFERENCES Parts(Id) ON DELETE RESTRICT,
    FOREIGN KEY (ModelId) REFERENCES Models(Id) ON DELETE RESTRICT
)

và reverse index:

CREATE INDEX IF NOT EXISTS IX_PartModels_ModelId_PartId
ON PartModels(ModelId, PartId);

Migration phải:
- tự động backfill mọi Models.PartId hiện có vào PartModels
- không tạo duplicate
- chạy lại nhiều lần vẫn an toàn
- không xóa Models.PartId trong migration đầu tiên
- không làm DB cũ mất khả năng mở
- không làm mất relation hiện tại.

Models.PartId coi là legacy compatibility field trong giai đoạn chuyển đổi.

KHÔNG thay đổi Tests.PartId và Tests.ModelId.
Mỗi Tests record vẫn phải lưu trực tiếp chính xác PartId + ModelId đã sử dụng tại thời điểm test để history/traceability không cần join PartModels.

4. PERFORMANCE RULE CHO TEST ENGINE

PartModels/database relation chỉ được resolve:
- khi load model
- khi chọn Part
- khi thay model/config
- hoặc khi startup/cache refresh.

KHÔNG được query PartModels trong continuity scan loop, resistance sampling loop, waterproof loop, USB communication loop hoặc relay timing path.

Nếu hợp lý, cache Part <-> Model relation và model metadata trong memory bằng cấu trúc thread-safe, invalidate cache khi relation/model thay đổi.

Real-time IO path phải ưu tiên tuyệt đối hơn database/report/history.

5. TRANSACTION

Audit quá trình hoàn tất một sản phẩm.

Nếu hiện tại đang commit từng record riêng, refactor để toàn bộ persistence của một completed test sử dụng transaction hợp lý:

Tests
TestFaults
ResistanceMeasurements
WaterProofMeasurements
TestHistory
counter/update liên quan

phải được commit atomically nếu kiến trúc hiện tại cho phép.

Dùng prepared/parameterized statements.

Không xây SQL bằng nối chuỗi.

Không giữ transaction mở trong suốt quá trình hardware test.
Chỉ mở transaction khi cần persist kết quả cuối hoặc checkpoint thật sự cần thiết.

6. SQLITE CONNECTION

Đảm bảo mỗi SQLite connection bật:
PRAGMA foreign_keys=ON;

Giữ WAL nếu đang sử dụng ổn định.

Đánh giá busy_timeout phù hợp để tránh lỗi database is locked.

Không tự ý đổi synchronous sang NORMAL/OFF chỉ để benchmark nhanh hơn nếu có thể giảm durability.
Nếu muốn thay đổi synchronous/cache/mmap/WAL checkpoint thì phải benchmark và giải thích trade-off trước, không tự áp dụng thay đổi rủi ro.

Không chạy VACUUM hoặc thao tác maintenance nặng trong lúc tester đang test sản phẩm.

Có thể dùng PRAGMA optimize ở thời điểm an toàn nếu phù hợp.

7. HISTORY PERFORMANCE

Không bao giờ load toàn bộ Tests/TestHistory vào WPF DataGrid.

History phải pagination, mặc định khoảng 50-200 rows.

Ưu tiên keyset pagination thay vì OFFSET rất lớn.

Ví dụ pagination dựa trên:
ResultAt + Id
hoặc Finished + Id

Đảm bảo index tương ứng phù hợp với ORDER BY/filter thực tế.

Danh sách history chỉ SELECT các column thực sự cần hiển thị.
FaultDetailsJson, LabelPayload, Full JSON hoặc text lớn chỉ load khi người dùng mở chi tiết.

Mọi query/report/export có thể lâu phải chạy ngoài WPF UI thread và không được block hardware test path.

8. TESTS + TESTHISTORY

Audit duplication giữa Tests và TestHistory.

Không được xóa TestHistory hoặc thay đổi format export hiện tại nếu chưa chứng minh backward compatibility.

Xác định rõ:
Tests + TestFaults + measurement tables = relational source of truth.
TestHistory = legacy/history/export snapshot nếu đúng với kiến trúc hiện tại.

Đảm bảo hai bên không thể bị ghi lệch nhau do transaction partial failure.

Tìm các trường JSON/text duplicate lớn gây database phình nhanh và đưa ra recommendation, nhưng không xóa dữ liệu compatibility mà chưa có migration/test.
